# MehmonGo: приём заявок, Telegram и супер-админка

**Дата:** 2026-08-31  
**Статус:** утверждённый дизайн перед планированием реализации

## 1. Цель первой рабочей версии

Перевести существующий англоязычный гостевой прототип из демонстрационного режима в рабочую систему для пилота в Kamilovs Hotel. Гость сканирует QR своей комнаты без регистрации, отправляет заявку, получает номер MehmonGo, а заявка сохраняется в базе и публикуется на русском языке в одной общей Telegram-группе команды.

В ту же версию входит защищённая супер-админка владельца MehmonGo. Через неё владелец создаёт отели, добавляет произвольные номера комнат, генерирует уникальные QR и скачивает готовые брендированные материалы A5.

## 2. Утверждённый объём

### Входит

- пилот для Kamilovs Hotel с архитектурой, поддерживающей несколько отелей;
- Supabase Postgres, Auth и Edge Functions;
- одна общая Telegram-группа для всех отелей;
- Telegram-сообщения на русском языке без кнопок назначения;
- гостевой сайт на английском языке без регистрации;
- уникальная защищённая ссылка для каждой комнаты;
- супер-админка только для владельца;
- создание, редактирование, включение и отключение отелей;
- добавление комнат по одной или вставкой списка, где каждая строка является отдельным номером;
- хранение процента партнёрского отеля для будущих расчётов;
- просмотр и фильтрация заявок;
- повторная отправка Telegram-уведомления из админки;
- общий многостраничный A5 PDF, отдельные PDF и PNG, ZIP всех материалов отеля;
- тесты гостевого потока, доступа, базы, Telegram-формата и QR/PDF.

### Не входит

- Telegram-кнопки назначения сотрудникам;
- аккаунты сотрудников или партнёрских отелей;
- онлайн-оплата;
- расчёт комиссий, выплат и прибыли;
- изменение статуса сотрудниками;
- импорт комнат из Excel;
- отдельные Telegram-группы для отелей.

## 3. Архитектура

```text
Гость открывает /r/<room_token>
        ↓
Сайт получает публичный контекст комнаты
        ↓
Гость отправляет форму
        ↓
Supabase Edge Function submit-request
        ↓
Проверка → PostgreSQL → Telegram Bot API
        ↓
Ответ с номером MG-XXXXXXXX
```

PostgreSQL является источником истины. Заявка сначала сохраняется, затем отправляется в Telegram. Ошибка Telegram не удаляет и не откатывает принятую заявку.

Админка использует Supabase Auth. Публичной регистрации нет. Первый пользователь создаётся владельцем проекта и получает роль `super_admin`. Админские операции разрешаются только активному супер-администратору через RLS и серверную проверку JWT.

## 4. Компоненты

### 4.1 Гостевой сайт

- маршрут `/r/<room_token>`;
- получение публичного контекста через read-only Edge Function `room-context`;
- четыре категории: tours, transport, restaurants, tickets;
- существующие категорийные поля формы сохраняются;
- клиент создаёт уникальный `idempotency_key` на попытку отправки;
- подтверждение показывается только после ответа сервера;
- интерфейс и ошибки остаются на английском языке.

`room-context` принимает только токен и возвращает минимальный набор данных: название отеля, обозначение комнаты и доступные категории. Он не раскрывает внутренние UUID, процент отеля или другие комнаты. Неизвестный либо отключённый токен возвращает 404.

### 4.2 Edge Function `submit-request`

Функция является единственной публичной точкой создания заявок. Она:

1. принимает `room_token`, категорию, поля формы, `idempotency_key` и скрытое honeypot-поле;
2. ограничивает размер тела запроса и длины строк;
3. проверяет активность отеля и комнаты;
4. повторяет клиентскую валидацию на сервере;
5. блокирует дубликат по `idempotency_key`;
6. вычисляет серверный HMAC-отпечаток комнаты и нормализованного контакта;
7. разрешает не более пяти принятых заявок с тем же отпечатком за десять минут;
8. создаёт уникальный публичный номер вида `MG-XXXXXXXX`, повторяя генерацию при редкой коллизии;
9. сохраняет заявку;
10. создаёт запись попытки Telegram-доставки;
11. отправляет сообщение в общую группу;
12. обновляет результат доставки и возвращает номер заявки.

Если Telegram недоступен, функция делает одну короткую повторную попытку. После повторной ошибки заявка остаётся принятой, а доставка получает статус `failed`. Админ может повторить отправку позже.

### 4.3 Edge Function `retry-telegram`

- требует действительный JWT супер-администратора;
- принимает ID существующей заявки;
- создаёт новую запись попытки доставки;
- не создаёт новую гостевую заявку;
- возвращает результат Telegram API без раскрытия токена.

### 4.4 Супер-админка

- `/admin/login` — email и пароль;
- `/admin` — количество активных отелей, комнат и новых заявок;
- `/admin/hotels` — список и создание отелей;
- `/admin/hotels/:id` — данные отеля, процент, статус и комнаты;
- `/admin/requests` — таблица заявок с фильтрами по отелю, комнате, категории, статусу и периоду;
- действие повторной отправки Telegram для неудачной доставки;
- генератор и скачивание материалов комнат.

Публичной формы регистрации нет. Неавторизованный посетитель любого маршрута `/admin/*` перенаправляется на `/admin/login`.

### 4.5 Генератор A5

Генератор использует утверждённый дизайн MehmonGo. Для каждой комнаты он формирует QR на URL `/r/<room_token>` и подставляет название отеля и номер комнаты.

Доступные результаты:

- PNG-превью выбранной комнаты;
- отдельный PDF A5 выбранной комнаты;
- общий PDF, где каждая комната занимает отдельную страницу A5;
- ZIP с индивидуальными PNG и PDF.

Генерация выполняется в браузере авторизованного администратора из SVG-шаблона и не требует постоянного хранения производных файлов. PDF- и ZIP-библиотеки работают только с уже загруженными данными выбранного отеля. Источником для повторной генерации служат данные комнаты, токен и версия шаблона.

## 5. Модель данных

### `admin_users`

- `user_id uuid primary key` → `auth.users.id`;
- `role text` со значением `super_admin`;
- `active boolean`;
- `created_at timestamptz`;
- `updated_at timestamptz`.

### `hotels`

- `id uuid primary key`;
- `slug text unique`;
- `name text`;
- `address text`;
- `commission_bps integer` — процент в базисных пунктах, например 1500 = 15%;
- `active boolean`;
- `created_at timestamptz`;
- `updated_at timestamptz`.

Ограничения: `commission_bps` от 0 до 10000.

### `rooms`

- `id uuid primary key`;
- `hotel_id uuid` → `hotels.id`;
- `label text` — произвольное обозначение комнаты;
- `public_token text unique` — криптографически случайный непрозрачный токен;
- `active boolean`;
- `created_at timestamptz`;
- `updated_at timestamptz`.

Ограничение: уникальная пара `(hotel_id, label)`. Индексы: уникальный `public_token`, `(hotel_id, active)`.

### `service_requests`

- `id uuid primary key`;
- `reference text unique`;
- `idempotency_key uuid unique`;
- `rate_limit_key text` — HMAC-отпечаток, не позволяющий восстановить контакт;
- `hotel_id uuid` → `hotels.id`;
- `room_id uuid` → `rooms.id`;
- `service_type text` — tours, transport, restaurants или tickets;
- `choice text`;
- `pickup text`;
- `destination text`;
- `requested_date date`;
- `requested_time time`;
- `party_size integer`;
- `guest_name text`;
- `guest_contact text`;
- `note text`;
- `status text` со стартовым значением `new`;
- `created_at timestamptz`;
- `updated_at timestamptz`.

Индексы для аналитики и фильтров: `(hotel_id, created_at desc)`, `(service_type, created_at desc)`, `(status, created_at desc)`, `(room_id, created_at desc)`, `(rate_limit_key, created_at desc)`.

### `telegram_deliveries`

- `id uuid primary key`;
- `request_id uuid` → `service_requests.id`;
- `attempt integer`;
- `status text` — pending, sent или failed;
- `telegram_message_id bigint null`;
- `error_code text null`;
- `error_message text null` с безопасным обрезанным сообщением без секретов;
- `created_at timestamptz`;
- `completed_at timestamptz null`.

Ограничение: уникальная пара `(request_id, attempt)`. Индекс: `(status, created_at)`.

```text

🚪 Комната: 205

💬 Комментарий: ...

```

Пустые необязательные строки не выводятся. Данные гостя не переводятся и экранируются для выбранного Telegram parse mode.

## 7. Ошибки и состояния

- неизвестный, отключённый или повреждённый QR → гостевая страница `This room link is unavailable`;
- ошибка валидации → ошибки конкретных полей без создания записи;
- повторный `idempotency_key` → возврат ранее созданного номера, без дубля;
- превышение лимита → HTTP 429 и понятное предложение связаться с администратором отеля;
- база недоступна → заявка не подтверждается, форма сохраняет введённые данные и предлагает повторить;
- Telegram недоступен после сохранения → гостю возвращается подтверждение, админка показывает `Telegram failed`;
- ошибка генерации одного A5-файла → остальные результаты не считаются готовыми, интерфейс показывает конкретную комнату и позволяет повторить.

## 8. Безопасность

- в публичном клиенте используется только Supabase publishable key;
- Supabase secret key и Telegram bot token существуют только в серверных secrets;
- таблицы в exposed schema получают RLS;
- анонимным пользователям запрещены прямые SELECT, INSERT, UPDATE и DELETE таблиц;
- публичная заявка создаётся только через Edge Function;
- админские политики проверяют активного `admin_users.user_id = auth.uid()` и роль `super_admin`;
- пароли обрабатываются только Supabase Auth;
- логи не содержат Telegram-токен, закрытый ключ или полный текст контакта;
- honeypot, ограничения длины и лимит частоты защищают публичную форму от базового спама;
- отключение отеля или комнаты немедленно делает соответствующий QR недоступным для новых заявок;
- QR-токены нельзя строить из ID, slug или номера комнаты.

Переменные окружения:

- `SUPABASE_URL`;
- `SUPABASE_PUBLISHABLE_KEY`;
- `SUPABASE_SECRET_KEY` — только сервер;
- `TELEGRAM_BOT_TOKEN` — только сервер;
- `TELEGRAM_CHAT_ID` — только сервер;
- `REQUEST_HASH_SECRET` — только сервер;
- `SITE_URL`.

Секреты не коммитятся в Git и не записываются в A5-файлы.

## 9. Тестирование

### Модульные тесты

- преобразование формы в серверный payload;
- серверная валидация каждой категории;
- формат номера `MG-XXXXXXXX`;
- русское Telegram-сообщение и экранирование;
- разбор списка комнат;
- построение `/r/<room_token>`;
- формирование A5 SVG/PNG/PDF.

### Интеграционные тесты

- создание заявки и связанной Telegram-доставки;
- повторный idempotency key не создаёт дубль;
- отключённая комната отклоняется;
- ошибка Telegram сохраняет заявку;
- retry создаёт новую попытку;
- RLS запрещает анонимное чтение и изменение;
- супер-администратор видит и изменяет разрешённые данные.

### Проверка артефактов

- размер каждой PDF-страницы соответствует A5;
- число страниц равно числу выбранных комнат;
- каждый QR программно декодируется в ожидаемый URL;
- PNG-превью визуально соответствует утверждённому шаблону;
- общий PDF и ZIP открываются без повреждений.

### Сквозной сценарий

1. супер-администратор создаёт Kamilovs Hotel;
2. добавляет комнаты 205 и 206;
3. скачивает общий A5 PDF;
4. QR комнаты 205 открывает правильный гостевой контекст;
5. гость отправляет транспортную заявку;
6. заявка появляется в базе и Telegram;
7. админка показывает ту же заявку, отель и комнату.
