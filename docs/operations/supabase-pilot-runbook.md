# MehmonGo pilot deployment

Status: local implementation; production deployment has not been performed.
Choose the MehmonGo project explicitly before running remote commands. Do not reuse another application's database or push local seed data into production.

## Prerequisites

- Reviewed application commit and passing application/SQL checks.
- Dedicated Supabase project reference, database password and CLI login. Create the project named for MehmonGo alone, in the region closest to the guests, and keep its database password in a password manager: Supabase shows it once and the CLI asks for it on every link.
- Telegram bot added to the agreed group with permission to send messages.
- Bot token and group chat ID supplied privately through Edge Function secrets.
- Owner Auth account and the final guest site origin.

CLI commands below were checked with the pinned Supabase 2.116.0 help on 2026-09-05. Current [secrets documentation](https://supabase.com/docs/guides/functions/secrets) describes built-in server credentials and environment-file import. Recheck the [changelog](https://supabase.com/changelog) before deploying a later version.

`supabase db reset --local` recreates the local pilot database and loads deterministic fixtures; use only on the disposable local instance. The database port for this project is 56322. Never reset a linked production database.

## Link and migrate

Set `MEHMONGO_PROJECT_REF` in the local process to the selected project reference. Use CLI login and a private password prompt; do not put credentials in command history or this document.

```powershell
npx supabase login
npx supabase link --project-ref $env:MEHMONGO_PROJECT_REF
npx supabase db push --linked --dry-run
```

Inspect the target reference, remote migration history, and proposed migrations before applying:

```powershell
npx supabase db push --linked
npx supabase migration list --linked
npx supabase db advisors --linked --type all --fail-on error
```

Do not pass `--include-seed`. Production room tokens must be generated by the database, not copied from local fixtures.

## Secrets and functions

Create an ignored `.env.production.secrets` file locally with `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `REQUEST_HASH_SECRET` and `SITE_URL`. Generate `REQUEST_HASH_SECRET` from at least 32 cryptographically random bytes. Never print or commit these values. Built-in `SUPABASE_SECRET_KEYS`/`SUPABASE_SERVICE_ROLE_KEY` stay exclusively in Edge Functions.

```powershell
npx supabase secrets set --env-file .env.production.secrets --project-ref $env:MEHMONGO_PROJECT_REF
npx supabase functions deploy room-context submit-request retry-telegram --project-ref $env:MEHMONGO_PROJECT_REF --import-map deno.json
```

Keep `verify_jwt = false` scoped to `room-context` and `submit-request`. `retry-telegram` requires a user JWT and independently verifies active super-admin membership. Never pass a blanket `--no-verify-jwt` flag when deploying all functions.

## Owner and pilot rooms

Create the owner account and its super-admin role in one step. Point the script at the production project and let it prompt for the password, which it reads without echoing and never writes to disk:

```powershell
$env:SUPABASE_URL = "https://$env:MEHMONGO_PROJECT_REF.supabase.co"
$env:SUPABASE_SECRET_KEY = "<project secret key, paste privately>"
node scripts/create-admin.mjs owner@example.com
node scripts/create-admin.mjs --list
```

Clear both variables from the session afterwards. Disable public sign-up for this owner-only administration app.

The same script removes an account created with the wrong address (`--remove owner@example.com`); it refuses to remove the last active administrator. To grant the role by hand instead, bind the verified Auth user UUID in a parameterized insert:

```sql
insert into public.admin_users(user_id, role, active)
values (:owner_auth_user_id, 'super_admin', true);
```

The SQL placeholder must be bound by the executing client; it is not executable raw dashboard SQL. For a dashboard query, replace it privately with the verified owner UUID as a UUID literal.

Create the pilot hotel and room through the super-admin once available. For first provisioning, this SQL generates a fresh token:

```sql
with pilot as (
  insert into public.hotels(slug, name, commission_bps)
  values ('kamilovs', 'Kamilovs Hotel', 0)
  on conflict (slug) do update set name = excluded.name
  returning id
)
insert into public.rooms(hotel_id, label)
select id, '205' from pilot
on conflict (hotel_id, label) do nothing;
```

Set the agreed commission separately; zero above is a bootstrap value, not a negotiated rate. Retrieve the stored room token through the admin. The QR URL is the final guest origin followed by `/r/` and that token.

## Guest hosting and smoke test

`vinext build` emits a Cloudflare Worker: `dist/server/wrangler.json` with `dist/client` as its asset directory. Two hosts can serve that output without changing the build.

- **OpenAI Sites hosting.** The project this repository was created from, recorded in `.openai/hosting.json`, and where the current public demo runs. Publish through that workflow.
- **Cloudflare Workers**, with your own account: `npx wrangler deploy --config dist/server/wrangler.json` after `npm run build`.

Vercel needs a different build target and is not supported by this configuration; moving there means replacing the Cloudflare Vite plugin and revalidating the whole build.

Set four build-time variables in the chosen host: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and `SITE_URL` with `VITE_SITE_URL` both holding the final guest origin. `SITE_URL` feeds page metadata; `VITE_SITE_URL` feeds the guest links and QR codes the admin generates, so a mismatch prints plaques that point at the wrong host. Never put the Supabase secret key, the Telegram token or `REQUEST_HASH_SECRET` in guest hosting: those belong only in Edge Function secrets. The URL must be stable before printing room plaques.

## Delivery uncertainty and rollback

`pending` means delivery is in progress or its outcome could not be recorded. Do not automatically resend it; inspect the group and delivery record first. Manual retry refuses pending and already-sent attempts to avoid duplicate notices. Failed requests remain stored even if Telegram is unavailable.

For rollback, restore the last known working site/function version compatible with the current schema. Keep additive migrations and request data; correct schema defects with reviewed forward migrations. Never use a factory reset, `db reset`, or destructive down migration as production rollback.

Rotate a bot credential through BotFather, update the Edge secret, and verify a test send. Rotate Supabase server credentials through project settings, then verify all functions. Coordinate `REQUEST_HASH_SECRET` rotation with the ten-minute quota window, because rotating it changes rate keys. Revoke owner sessions before removing admin access when responding to an account incident.
